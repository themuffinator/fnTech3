# Jedi Academy siege's round record and sky portals, 2026-10-15

The [compatibility round of the same day](2026-10-15-compatibility-round.md)
left two Academy multiplayer refusals. Every siege game (`g_gametype 7`)
stopped on the server at game import 43, `G_SIEGEPERSGET`. `mp/siege_hoth`
in a free-for-all stopped on the client at a view flag the adapter did not
serve. This slice serves both: the siege round record the game keeps from
one level to the next (imports 42 and 43), and the scene a level's sky
portal draws (Raven's view flag `0x8`), with the snapshot rule that sends
the portal's entities. The [JSON companion](2026-10-15-jka-siege.json)
records the binaries, retail identities, commands and outcomes. No
compatibility gate closes.

Implementation is independently authored. Retail `jamp.exe` 1.01 and the
1.01 modules in `assets3.pk3` were read with capstone. Pinned OpenJK was
used only to locate routines and names (reference observation; no text
incorporated).

## The siege round record

### Observed, retail `jamp.exe` 1.01

- The game dispatcher (`0x45a660`) bounds the import at `0x27a` and jumps
  through the table at `0x45d34c`. Import 42 lands at `0x45ae89`, import 43
  at `0x45aeb3`.
- Import 42 takes the module's pointer (`VM_ArgPtr`, `0x44adf0`) and copies
  three words from it into `0x12a4d34`, `0x12a4d38` and `0x12a4d3c`.
  Import 43 copies the same three words back. Both answer 0. Neither checks
  the pointer, so a null record reads or writes address 0 and faults.
- The three words sit beside the game's VM pointer (`gvm`, `0x12a4d30`), in
  the image's zero-filled data (the section's file data ends at `0x573000`).
  A sweep of the whole code section finds nothing else that reads or writes
  them. No fixed clear covers them either: `SV_ClearServer` wipes the level
  (`0xb934e0..0xc317bc`, `0x45e73c`) and `SV_Shutdown` the server
  (`0xc317c0`, `0xa048` bytes, `0x45f406`), both elsewhere.
- So the record starts zeroed with the process. It survives map changes,
  restarts, server shutdowns and the game module's own reloads, as the run
  below confirms.
- The retail game (`jampgamex86.dll` 1.01) calls each import through one
  wrapper (`0x200a6330` pushes `0x2a`, `0x200a6350` pushes `0x2b`), always
  with its own 12-byte record (`0x20576ed8`).
  - It reads the record as a siege level starts, when the gametype is 7 and
    `g_siegeTeamSwitch` is set (`0x200a1595`).
  - It sets it at four sites: three clear it (`0x200a1f46`, `0x200a1f99`,
    `0x200a21ad`) and one stores `{1, team, time}` (`0x200a1fc4`).
- The words are a flag, the team that set the time and the time to beat.
  The second round of a siege map is another level, and this record is how
  it learns the time.

### Retail and fnTech3 side by side

A synthetic game module (`.tmp/jka-siege/probe/siege-probe.cpp`)
calls both imports across the engine's own level changes. It reads into a
buffer filled with `0xa5` and prints the four bytes on either side of the
record, and it carries its stage in a cvar because each level reloads it.
It ran on retail `jamp.exe` 1.01 as a dedicated server and on fnTech3's
dedicated server.

| Stage | Retail `jamp.exe` 1.01 | fnTech3 before (`fbde92d4`) | fnTech3 after (both runtimes) |
| --- | --- | --- | --- |
| first level, first read | `0,0,0`, answer 0 | refused at import 43 | `0,0,0`, answer 0 |
| set `1,2,345678`, read | same words, answer 0 | -- | same |
| after `map`: read, set `7,-1,INT32_MIN`, read | `1,2,345678`, then the new words | -- | same |
| after `map_restart 0`: read | `7,-1,INT32_MIN` | -- | same |
| after `killserver`, `map`: read, clear, read | `7,-1,INT32_MIN`, then `0,0,0` | -- | same |

Every guard byte stayed `0xa5`, and the module's own record was unchanged
by each set, on both engines. Only the level time each level starts at
differs. Retail passed 5400 to the level after the map change, and 6550
after the restart. fnTech3 passed 0 and 500. That is outside this record;
see the findings below.

### Implemented

- `fntech3_jka_siegePers_t` (`code/compat/jka_game_abi.h`), 12 bytes. Its
  three words are pinned in `code/compat/jka_wire_layout.def` and asserted
  in `tests/jka_abi_layout_tests.cpp`, now 11 records and 379 members.
- `code/server/server_jka_game.hpp` keeps one record for the process.
  Imports 42 and 43 copy its twelve bytes each way after the module's
  bounds check and answer 0. `SV_JKAClearGame` leaves the record alone, as
  retail leaves its words.
- A null record is refused by name instead of faulting. The dispatcher
  serves 159 imports.
- `tests/jka_siege_persistence_tests.py` compiles the dispatcher's own two
  cases, the record and `SV_JKAClearGame`. It runs them against a QVM data
  segment and a native module's memory, with bounds, null and clearing
  cases. Seven mutations of the cases are each caught.

## The sky portal's scene

### Observed, the retail client game (`cgamex86.dll` 1.01)

- `CG_DrawActiveFrame` (`0x300639b2`) clears the view (`0x300634ab`). It
  then draws the level's sky portal (`0x30063b8c`, function `0x30062390`)
  before anything else, and the view it is seen from last (`0x30063e17`,
  function `0x3002de20`).
- The portal's scene is the view moved to the portal's camera, with flags
  `0x18` (`0x30062719`). The world view adds `0x10` (`0x3002df11`).
- The portal's scene runs before the snapshot's area mask is copied into
  the view (`0x30063c35`), so its mask is empty.
- The other scenes it submits carry `0x1` (models, `0x30023409`), `0x5`
  (hyperspace, `0x3006382e`) and `0x21` (the automap, `0x300631a3`).
- When a level's portal says `onlyfoghere`, `0x40` moves from the portal's
  scene to the world view (`0x300627ef..0x300627fb`).
- The 1.01 client game never sets `0x80` (force sight), which OpenJK's
  source does.
- Three of the installation's multiplayer maps have a `misc_skyportal`:
  `mp/duel6`, `mp/duel9` and `mp/siege_hoth`. None names `onlyfoghere`, a
  field of view, fog or an orient entity. Nine single-player maps have one
  as well; single player is outside this record.

### Observed, retail `jamp.exe` 1.01's renderer

- **The flag.** `RE_RenderScene` (`0x4abc90`) sets a level-wide flag the
  first time a scene with `0x8` arrives (`0x105361c`, `0x4abe18`). It keeps
  `0x10` per scene (`0x1053618`, `0x4abe23`). Loading a world clears the
  flag (`0x490fc3`).
- **What the flag stops.** While it is set, every scene but a portal's own
  draws no sky. `RB_EndSurface` drops every surface of the sky stage
  iterator (`0x4af5c9..0x4af5e7`, iterator `0x4b9690`), and the iterator
  itself returns at once (`0x4b96ad`). The portal's picture, already in
  the frame, shows wherever the sky would have been.
- **Clears.** A latched world view clears no colour first
  (`RB_BeginDrawingView`, `0x48a70d`). A portal's scene clears to grey only
  under `r_fastsky` or without a world.
- A portal's scene without `0x10` would draw only its sky surfaces
  (`0x4af5ef`). The client game never sends one.
- A portal's scene draws no weather (`RB_RenderWorldEffects`, `0x488ead`).
- The scene frame time is taken from every scene, the portal's included
  (`0x4abdff..0x4abe0c`); OpenJK's source skips the portal's. Only the
  weather reads it (`0x488ee1`).
- **The server.** `SV_AddEntitiesVisibleFromPoint` sends any entity whose
  state says `isPortalEnt` (`+0x108`) unconditionally (`0x46105c`). The
  test comes after the broadcast, own-entity and named-client rules and
  before any test of what the viewer can see. The retail game marks the
  entities its portal can see 1,050 ms after the portal spawns:
  `misc_skyportal`'s spawn (`0x20093ca0`) schedules the pass
  (`0x20093d80`), which marks every non-client entity, and any NPC, in the
  portal's PVS with a clear line to it (`0x20093c67`).

### Implemented, on fnTech3's own renderers

- **The adapter** (`code/compat/jka_render_adapter.hpp`). A view with `0x8`
  and `0x10` crosses as the engine-owned `refdef_t.jka.skyboxPortal`
  (`code/renderercommon/tr_types.h`); no Quake III flag stands for it.
  - A view the adapter refuses now names its first unserved flag and the
    word itself: the automap (`0x20`), no global fog (`0x40`), force sight
    (`0x80`), a bit Raven never named, or a portal's scene without its world.
- **The rule** (`code/renderercommon/tr_jka_sky_portal.h`). All three
  renderers apply it in `RE_RenderScene`, through the scene's own draw-sky
  word, which `RB_StageIteratorSky` already reads (the RTCW portal path
  uses the same word).
  - A portal's scene marks the level and draws its own sky; every other
    view of the level then draws none.
  - The mark lives in `tr`, which `R_Init` clears before every world load,
    because the client restarts its renderer for each level. That stands
    for retail's clear.
  - Fn's Academy world views never clear the colour, so the portal's
    picture survives.
- **Fn features.** The portal's scene is an ordinary Fn world view: Fn's
  lighting, shadows, fog, bloom and static map lights apply to it.
  - The RTX renderer's path tracer leaves the portal's scene to raster and
    keeps raster's pixels wherever a traced ray meets sky, as it does for
    RTCW's.
  - The underwater medium is the eye's. The client takes no sample at the
    portal's camera, and the portal's scene takes no medium of its own, so
    the once-a-frame underwater pass waits for the eye's view.
  - The local view's liquid ripples ignore the portal's camera. The entity
    editor does not take the portal's view for the player's.
- **Left out.**
  - Retail's grey clear of a portal scene under `r_fastsky`: Fn's fast sky
    draws no sky in either scene and keeps its own clear.
  - Weather, which Fn does not draw for this profile, and with it the
    scene frame time only retail's weather reads.
- **The snapshot** (`code/server/server_jka_snapshot.hpp`). An entity
  marked `isPortalEnt` is sent after the existing broadcast rules and
  before the visibility tests, as retail sends it.
- **Tests.**
  - `tests/jka_sky_portal_tests.py` runs all 256 combinations of Raven's
    named flags through the adapter, and a level's frames through each
    renderer's own scene lines sliced from its `tr_scene.c`. Ten mutations
    are each caught.
  - `tests/jka_render_tests.cpp` now serves `0x18`, `0x19`, `0x1c` and
    `0x1d` and refuses the rest.
  - `tests/jka_snapshot_tests.cpp` covers the portal entity rule.

### Live

Clients ran windowed, on a private desktop, with no network sockets, as
spectators, with no input. Each ran on its own home, and the installation was
unchanged. The before and after runtimes were built from an export of
`fbde92d4`, without and with this slice. The final runtime is an export of
`34ecbab5` with this slice.

| Map, game | Before | After and final |
| --- | --- | --- |
| `mp/siege_hoth`, siege | server stops at import 43 | reaches play; the client stops at UI menu 11 |
| `mp/siege_desert`, siege | server stops at import 43 | reaches play; the client stops at UI menu 11 |
| `mp/siege_korriban`, siege | server stops at import 43 | reaches play; the client stops at UI menu 11 |
| `mp/siege_hoth`, free-for-all | `unsupported Raven renderer view flags` | reaches play; stops at renderfx `0x80040` |
| `mp/duel6`, free-for-all | `unsupported Raven renderer view flags` | plays to the probe's end (final) |
| `mp/duel9`, free-for-all | `unsupported Raven renderer view flags` | plays to the probe's end |

- **The new frontiers.** Menu 11 is Raven's class menu (`UIMENU_CLASSSEL`
  in its enumeration), which the client game opens in a siege game. Renderfx
  `0x80000` is `RF_SETANIMINDEX`, an animated stage whose frame the entity
  picks.
- **The after runtime on `mp/duel6`.** It took one capture, then stopped at
  the dust effect's Sound primitive, which the final runtime's base serves.
- **`mp/duel6` on the final runtime.** It was captured from the spectator's
  place `(-2224 0 924)`, looking along yaw 0, in all three renderers. The
  sky patch at the top left (pixels 40..300 by 5..60) has these mean
  colours:

  | Renderer | Mean colour |
  | --- | --- |
  | GLx | `(239, 243, 248)` |
  | Vulkan | `(241, 245, 248)` |
  | RTX | `(250, 252, 254)` |

  The RTX renderer's raster is brighter with its default bloom.

- **The mechanism on `mp/duel6`.** The same view was taken with two
  diagnostic GL renderers built from the final export's source and used
  only here. One turns the rule off. The other draws no portal scene at
  all, though the rule stays on. The sky patch then reads:

  | Variant | Mean colour |
  | --- | --- |
  | rule on (final) | `(239, 243, 248)` |
  | rule off | `(139, 148, 168)` |
  | no portal scene | `(67, 82, 59)` |

  - **Rule on.** The patch shows the portal's picture. The portal room
    holds sky surfaces and a cloud-layer patch near its camera, by the
    map's own surface list.
  - **Rule off.** The view draws its own sky box over that picture, blue
    with the level's clouds.
  - **No portal scene.** The region is left undrawn and keeps earlier
    frames.
  - Rule on and rule off differ by more than 24 levels in 56,602 pixels,
    all within rows 0 to 290, the upper part of the view where the sky
    shows.
  - No retail picture was taken: the retail client asks for disc 1 before
    it connects, even to a listen server.

- **`mp/duel9`'s grey sky.** The sky shows a flat `(82, 82, 82)`, and not
  because of the portal. The level's sky shader, `textures/mp/s_hothsky`, is
  `(DEFAULTED)` in `shaderlist`. Its general section says `sun`, which
  Fn's parser (Quake3e's) does not know, so it rejects the whole shader.
  - The sky polygons then draw as the default image, an ordinary opaque
    surface, in both views.
  - The region keeps that one colour with the rule on, with it off, with no
    portal scene at all, under `r_fastsky 1` and under `r_showsky 1`.
  - 59 of the installation's shaders carry that line, 58 of them skies,
    among them `mp/siege_hoth`'s `textures/siege/hoth_sky`. Raven's renderer
    parses `sun` with `q3map_sun`.
  - This is open, and outside this slice.

## Remaining and unrelated findings

- **Siege's next stop.** A siege game stops when the client game opens UI
  menu 11, the class menu. fnTech3 maps menus 0 to 5 to its own
  (`code/compat/jka_ui_exports.h`) and refuses 6 to 11 by number. In
  Raven's enumeration those are force powers, siege's message and
  objectives, voice chat, close-all and class selection.
- **`RF_SETANIMINDEX`.** `mp/siege_hoth` in a free-for-all stops at Raven's
  `RF_SETANIMINDEX` (`0x80000`).
- **Defaulted skies.** Fn's shader parser defaults the 59 installed shaders
  whose general section says `sun` (58 skies), so their maps' skies draw
  grey. This holds wherever such a sky is used, not only through a portal.
- **Other refused view flags.** The automap (`0x20`) and no-fog (`0x40`)
  view flags stay refused, now by name. The 1.01 client game never sends
  `0x80`.
- **Broadcast exclusion.** Fn's Academy snapshot rule excludes a
  `SVF_BROADCASTCLIENTS` (`0x2`) entity from clients it does not name, as
  OpenJK's source does. Retail `jamp.exe` 1.01 has no such exclusion: its
  loop reads the flags word only for the no-client and single-client tests
  (`0x460fae`) and the broadcast test (`0x461011`). The mask only adds
  (`0x46104f`).
- **Level time after a map change.** The synthetic module saw the level
  time a level starts at differ. Retail passed 5400 to the level after a
  map change, and 6550 after a restart of it. fnTech3 passed 0 and 500.
  Not examined further.
- **First-world-view passes.** Fn's once-a-frame passes take the frame's
  first world view, which on a portal level is the portal's scene: motion
  blur (`FBO_MotionBlur`, off by default), the screen copy for
  `$screenMap` stages (`frameSceneNum == 1`) and the cube-map screenshot
  (`screenshot cubemap`). That also holds for RTCW's and ET's portal skies. For Academy, the underwater pass now waits for the
  eye's view; RTCW's and ET's portal scenes still sample the medium and
  liquid motion at their own cameras.
