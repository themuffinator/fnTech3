# Jedi Outcast multiplayer: its records, its imports, and its level

*2026-09-22. Measured from a legitimate retail Jedi Outcast 1.02a installation
and its own `jk2mp.exe`. The installation was read, never written. Raven
released no multiplayer source for this title, so every number below was read
out of the retail binaries themselves, and the method is given so it can be
checked.*

## The entity state, whole

**Jedi Outcast multiplayer's `entityState_t` is 296 bytes and all 74 of its
members are now named.**

The engine carries its own delta table: an array of
`{ const char *name; int offset; int bits; }`, which is how every engine in
this line describes the record it sends. Outcast's begins at file offset
`0xf5ab0` in `jk2mp.exe` and holds **73 triples**. Sorted by offset they cover
**every four-byte slot from 4 to 292 with no gap at all**, which means the
table is not a subset of the record — it *is* the record, from 4 onwards.

Offset 0 is not in it, and that is expected: no engine in this line
delta-codes an entity's own number, because the number is the index the entity
is sent under. Offset 0 is `number`.

The last member, `generic1`, sits at 292 and is four bytes wide, so the record
ends at **296** — which is exactly the size measured separately and by an
unrelated means, from what the engine's own brush-model writer does. Two
methods, one answer.

The table also types every member. A member sent at **zero bits** is a float:
that is this lineage's own convention for "send the whole thing", and the
members it applies to are precisely the ones a float belongs in —
`pos.trBase[0..2]`, `pos.trDelta[0..2]`, both angle vectors, both origins and
`speed`. Everything else carries a bit width between 1 and 32 and is an
integer. Nothing here is typed by guesswork.

The result is frozen in `code/compat/jk2_game_abi.h` and held to the table by
`tests/jk2_abi_layout_tests.cpp`, which asserts every offset, every width and
every kind at compile time.

### It is not Jedi Academy's

Outcast's entity state is 296 bytes; Academy's is 532. The two share many
member *names* — `saberMove`, `forcePowersActive`, `trickedentindex` — and the
same general order, but Academy added members throughout and the offsets
diverge from `bolt1` onwards. The layout test states the difference as an
assertion so that nothing can later be shared between the two on the grounds
that they look alike.

### The engine's own half of the entity

The hundred bytes after the state are the engine's, and ten of their thirteen
members are now read out of the retail engine's own link and unlink routines,
at `0x4502d0` and `0x450270`:

| member | how the engine shows it |
| --- | --- |
| `linked` | `mov [esi+0x128], 1` when it links, zeroed when it unlinks |
| `linkcount` | `inc dword [esi+0x12c]` |
| `bmodel` | tested at `[esi+0x138]` before the solid size is encoded |
| `mins`, `maxs` | read at `0x13c`-`0x144` and `0x148`-`0x150` for that encoding |
| `contents` | tested at `[esi+0x154]` against the solid and body bits |
| `absmin`, `absmax` | written at `0x158` and `0x164`, each the sum of the two below |
| `currentOrigin` | read at `0x170`-`0x178` |
| `currentAngles` | read at `0x17c`-`0x184`, to decide whether the box is turned |

Subtracting the state's 296 gives 0, 4, 16, 20, 32, 44, 48, 60, 72 and 84 —
which also confirms, from a third direction, that the engine's half begins at
296.

What is left is `svFlags`, `singleClient` and `ownerNum`. Their *offsets* are
not in doubt: 8 and 12 are the only slots between the evidenced `linkcount` at
4 and the evidenced `bmodel` at 16, and 96 is the only slot before the measured
hundred-byte end. Which of the three sits where is read from Quake III's order,
and it is the one thing in this record not separately evidenced. The header
marks each line `evidenced` or `placed` so the difference is visible where the
numbers are used.

## The player state, and its ping

The same scan finds the player delta table at `0xf5e20`, **105 triples** from 0
to 1364. `lastHitLoc[2]` at 1364 is four bytes, so that record ends at
**1368** — again exactly the size already measured by another means.

Unlike the entity table this one has gaps, because arrays are not delta-coded
member by member: `stats`, `persistant`, `powerups`, `ammo` and the force data
appear only where individual members are sent. What it does name is
substantial: the whole movement and view prefix, both event slots, the saber
and force state, the duel and zoom state.

**`ping` is at offset 484.** It is not in the table, because no engine in this
line delta-codes a ping. It was read instead out of the one place the engine
writes it. Retail `jk2mp.exe`'s ping pass:

    0x44efe9  cmp  eax, 0x3e7              ; 999
    0x44efee  mov  [esi], eax              ; cl->ping = total / count
    0x44eff2  mov  dword ptr [esi], 0x3e7  ; ... or 999
    0x44effd  call 0x44a720                ; the client-state accessor
    0x44f002  mov  edx, [esi]
    0x44f007  mov  [eax + 0x1e4], edx      ; ps->ping = cl->ping

and the accessor it calls is nothing but the array it is named for:

    0x44a720  mov  eax, [0xb7a0cc]         ; stride
    0x44a725  imul eax, [esp + 4]          ; times the client number
    0x44a72a  add  eax, [0xb7a0c8]         ; plus the base
    0x44a730  ret

`0x1e4` is 484. The engine's checked game-data view now writes Outcast's ping
there instead of refusing to write one.

## What the module asks for: 97 imports, and no others

Outcast's game module is a QVM, not a DLL, so it has no call wrappers to
count. It has something equivalent. A QVM reaches the engine by pushing a
**negative** address and issuing `OP_CALL`; the virtual machine reads a
negative program counter as the system call `-1 - address`, and writes that
number into the argument block itself. So the complete set of imports the
module can ever reach is the set of negative constants it calls, and the
argument count is the widest `OP_ARG` offset written before the call.

`vm/jk2mpgame.qvm` calls **97 distinct imports**:

| run | how many | which |
| --- | --: | --- |
| 0 | 42 | 0-26, 28, 30-34, 36-39, 42, 47-50 |
| 100 | 9 | 100-106, 110, 111 |
| 200 | 5 | 200, 201, 209, 210, 211 |
| 300 | 1 | 303 |
| 400 | 16 | 400, 401, 406-409, 411, 414, 416-419, 421, 422, 424, 425 |
| 500 | 24 | 525, 526, 542, 546-548, 551, 555, 556, 561-563, 584, 586-593, 595, 596, 599 |

That is the whole of this title's module boundary: not an estimate of the work
left, but its bound. Retail `jk2mp.exe` *handles* 221 numbers; its own game
module uses 97 of them.

### Which blocks are shared with Jedi Academy, and which are not

Academy's 150 imports were counted the same way, from its DLL's call wrappers,
and the argument counts of both can be compared. Of the 70 numbers both
modules call, 41 agree on how many arguments they pass — but the agreement is
not spread evenly, and where it falls is the finding:

- **The elementary-action block at 400-425 agrees on every single number**:
  all sixteen that both modules call pass the same number of arguments.
- **The AI-state block agrees on every single number**: 525, 526, 546, 547,
  548, 551, 555, 556, 561, 562 and 563, eleven for eleven, including the two
  that take no argument at all.
- **The block at 0 does not agree**, and not marginally: `G_CVAR_REGISTER` is
  four arguments in Academy and two in Outcast, `G_FS_FCLOSE_FILE` one and
  five. Raven renumbered the low block between the two titles, which is why
  fnTech3 established Outcast's run at 0 from what `jk2mp.exe`'s own handlers
  do rather than from Academy's names.
- **The Ghoul2 block at 584 and above does not agree either**: 587 matches at
  nine arguments, but 589, 590, 591, 595 and 596 all differ. Academy added
  Ghoul2 imports and shifted what came after them.

An agreeing argument count is evidence for a correspondence and never proof of
one. It is recorded here as what it is, and no Outcast import is served on the
strength of it.

### What it says about this title's bots

Outcast's installation ships `botfiles/` with **35 `.jkb` bot characters and
`bots.txt`** — Raven's own format — and **none** of Quake III's `items.c`,
`weapons.c`, `syn.c`, `rnd.c` or `match.c`, and **no `.aas` file for any of its
41 maps**. So none of Quake III's four configured AI subsystems has a file to
read, and area awareness has nothing to load, whatever the numbering says.
This title's profile claimed `COM_BOT_AI_QUAKE` and now says what was
measured, exactly as Academy's does.

## The first run is Quake III's, handler by handler

Each handler in the retail dispatcher says how many arguments it takes and how
many of them it converts from module addresses to real pointers. For the world
block that is enough to name every one, and two of them name themselves:

| import | arguments | pointers | what its handler does |
| --: | --: | --: | --- |
| 23 | 2 | 2 | a brush model, by entity and name |
| 24 | 9 | 5 | the trace, at `0x450b00` |
| 25 | 2 | 1 | the contents at a point |
| 26 | 2 | 2 | whether two points share a visibility set |
| 28 | 2 | 1 | an area portal's state |
| 30 | 1 | 1 | **calls `0x4502d0`** |
| 31 | 1 | 1 | **calls `0x450270`** |
| 32 | 4 | 3 | the entities in a box |
| 33 | 3 | 3 | whether one entity touches a box |

`0x4502d0` and `0x450270` are the same two routines the engine's own `linked`
and `linkcount` offsets were read out of above, so 30 and 31 are not a
resemblance argument at all: they are link and unlink by identity. The module's
own argument counts agree with Quake III's for all thirty-one numbers of the
first run it calls.

### The trace is Quake III's, and Academy's is not

This is the one worth stating on its own, because the same question got the
opposite answer in the other title. Retail `jk2mp.exe`'s trace routine hands
the module's record to the collision tracer, then reads the fraction back at
**eight** bytes into it and writes the entity number at **fifty-two** -- both
exactly where Quake III keeps them. Its module passes Quake III's **seven**
arguments, where Academy's passes nine.

Jedi Academy's trace, measured the same way from the other side, is 48 bytes
with the two solid flags and the entity number packed into the first four. Had
either title's answer been assumed from the other, every trace in that game
would have been wrong and nothing would have said so.

### Recorded motion paths sit five numbers lower

Academy puts them at 52-56; Outcast puts them at 47-51. That is read, not
shifted: the routine trap 48 calls is the one that reports
`^1ROFF System Error:`, and the `ROFF` name itself is referenced from the same
run of code. Their argument counts agree with Academy's block member for
member -- nothing, nothing, a name, three numbers, one number.

### The run at 200 is the bot library, where Academy's is navigation

Handler 200 checks whether bots are enabled, then whether the library was ever
bound, and if not prints `Error: SV_BotLibSetup without SV_BotInitBotLib` --
the retail engine names the function itself -- before tail-jumping into the
library's own setup. 201 is the same shape for the shutdown. The five numbers
the module calls in that run are 200, 201, 209, 210 and 211, whose argument
counts match Quake III's setup, shutdown, snapshot entity, console message and
user command exactly.

Academy's run at 200 is Raven's navigation graph, twenty-three imports of it.
The two titles have nothing in common there.

## Where the module stops

It does not stop any more. The retail QVM loads out of the pak, initializes,
prints Raven's own `gamedate: Mar 04 2002` and its serverinfo, publishes its
arrays, registers 21 items, parses 29 bots and 15 arenas, spawns `ffa_bespin`
and holds it open through its frame loop with **no import refused**. Starting a
recorded motion path is the one call deliberately left refused, for the same
reason it is in Academy: how an entity should move along one is not measured.

## The run at 500, mapped from the engine's own handlers

Retail `jk2mp.exe`'s dispatcher is a byte index table at `0x44cc50` and a jump
table at `0x44c8d8`, so each import's handler can be read on its own. For the
twelve of the 500 run the module actually calls, the handler says how many
arguments it takes, how many of them it converts from module addresses to real
pointers, and what it hands them to:

| import | arguments | pointers | passes to |
| --: | --: | --: | --- |
| 584 | 1 | 0 | answered inline |
| 586 | 9 | 5 | `0x4a7620` |
| 587 | 9 | 5 | `0x4a7620`, the same routine |
| 588 | 7 | 2 | `0x4a6e90` |
| 589 | 3 | 1 | `0x4a75a0` |
| 590 | 3 | 0 | `0x4a75f0` |
| 591 | 11 | 3 | `0x4a7520` |
| 592 | 10 | 1 | `0x4a7440` |
| 593 | 3 | 1 | `0x4a7d80` |
| 595 | 4 | 0 | `0x4a7bf0` |
| 596 | 2 | 1 | `0x4a7ce0` |
| 599 | 1 | 1 | `0x4a6e00` |

**Every one of those argument counts matches what the module's own bytecode
writes** — eleven for eleven, counted from the other side of the boundary by a
completely different method. That is a check on the method as much as on the
numbers: the QVM scan and the engine's handlers were read independently and
agree everywhere they overlap.

**588 is the Ghoul2 model initializer**, and it is the one served. Its handler
converts the first two arguments and passes them with five more to
`0x4a6e90`, which measures the second as a string, tests whether the first
points at a null pointer, and if so allocates an instance and stores it back
before loading the named model into it. That is the same call Jedi Academy
makes at 590, and fnTech3's server-side Ghoul2 store answers both.

586 and 587 share one routine and both pass nine arguments with five pointers,
which is the shape of Academy's two bolt-position calls at 587 and 589. They
are recorded here and not served: a shape that matches is a reason to look, not
a reason to answer.

## Its bots, as far as they get

`addbot Reborn 3` on a running server walks the same path Jedi Academy's does,
and the engine work it needed was almost all shared. Five more imports were
named from the retail dispatcher and served:

| import | what its handler does | Academy's number |
| --: | --- | --: |
| 34, 35 | Quake III's bot client allocate and free, at Quake III's numbers | 38, 39 |
| 584 | walks the instance's models, returns true at the first not removed | 585 |
| 589 | bounds-checks the model index, hands a name to a lookup over two lists inside it | 593 |
| 590 | bounds-checks the same way, stores one int inside the model | 594 |
| 525-563 | eleven calls that reach the same bot-library export table the setup at 200 reaches | the same eleven |

The eleven AI-state calls are at the same numbers Academy uses, and that is not
taken on resemblance: each handler reaches the export table at `0xb0d230` --
the one the setup call at 200 reaches -- and the four that were read have the
shapes the allocators have. 546 takes a client number and returns what it made,
547 takes one and returns nothing, and 555 and 561 take none at all. Their
slots in that table, `0x198`, `0x19c`, `0x1c0` and `0x1dc`, sit in the order
the library declares its goal, move and weapon calls in.

### The input frame, measured from the client that builds one

Import 36 needed this title's `usercmd_t`, and the engine is no help with it:
the record is **28 bytes** and the engine copies it whole -- its own reader is
a `rep movsd` of seven dwords, and every other place it touches one does the
same -- so it never reads a field, and nothing about the *inside* of those 28
bytes follows from the engine at all.

The client that *builds* a command does read every field. At `0x4076c0`:

| offset | how it is written | field |
| --: | --- | --- |
| 0 | `mov [ecx], eax` from the client's own time | `serverTime` |
| 16 | built by OR-ing bits, `or [edx+0x10], 0x100` and a shifted mask | `buttons` |
| 20 | `mov [ecx+0x14], al` from its own global | `weapon` |
| 21 | `mov [ecx+0x15], al` from its own global | `forcesel` |
| 22 | `mov [ecx+0x16], al` from its own global | `invensel` |
| 23 | `mov [ecx+0x17], al`, and that global cleared right after | `generic_cmd` |
| 24-26 | three bytes written together, in two other places | the three moves |

The clearing at 23 is what identifies *which* field it is rather than merely
that one is there: a value written and then wiped is a command that fires once.
With `serverTime` at 0 and the first byte field at 20, only 4, 8 and 12 remain,
and they hold the view angles. Twenty-seven bytes of members, padded to 28.

It comes out the same shape as Jedi Academy's, and that is worth saying plainly
because it was not assumed from the shared size: Academy's was frozen from its
own measurement, and this was read out of Outcast's own client before the two
were ever compared. Quake III's is 24 bytes and is neither of them.

### Where its bot stops

With that record frozen and its adapter written, the elementary-action block
and the two remaining bot-library calls could be served. All sixteen actions
reach the export table at `0xb0d230` -- the one the setup call at 200 reaches
-- at slots `0xac`, `0xb0`, `0xb8` and `0xbc` for move, view, get-input and
reset-input, which are consecutive in that library's own declaration order.
Import 211 computes `&clients[n]` by the client stride and hands it a converted
pointer, which is this engine's own client think; 210 is the console message.
209, the snapshot entity, stays refused, because there are no snapshots to read
one out of.

### Its bots play

**Two bots play a retail Jedi Outcast multiplayer match, with nothing
refused.** Ninety seconds of `ffa_bespin` with `Reborn` and `Tavion` in it: two
clients connect, change their userinfo, enter, begin, and collect seventeen
items between them -- blasters, a rocket launcher, a flechette, ammunition and
a medpac -- with no unserved import and no error.

Two more measurements got it there.

**The four arrays in the player state, named by the engine itself.** The delta
table names 105 fields and leaves a 276-byte hole where the arrays live. The
engine's own delta reader walks them, and in a developer build it prints what
it is walking: `PS_PERSISTANT` before the loop at 280, `PS_AMMO` before the one
at 408, `PS_POWERUPS` before the one at 344. Each loop runs sixteen times, and
the powerups loop calls a different reader from the other three -- long words
where they read shorts -- which is what a powerup is, a time rather than a
count. The first loop, at 216, is the one left: stats.

    216  stats       16 shorts
    280  persistant  16 shorts   (engine prints PS_PERSISTANT)
    344  powerups    16 longs    (engine prints PS_POWERUPS)
    408  ammo        16 shorts   (engine prints PS_AMMO)

That accounts for 680 of the record's 1,368 bytes. The other 688 have no name
in any table this engine has read, so the record declares them as unnamed spans
and the reader does not carry them. **There is deliberately no way to write one
of these**: a write would put zeroes over half a record it cannot name. Nothing
in the engine writes a player state for this title -- the ping goes in at its
own measured offset, not through the adapter -- and if something ever needs to,
the rest has to be measured first. Jedi Academy's player state is carried
whole, all 168 fields; the difference between the two is the difference between
what has been measured for each.

**A pass entity of -1.** With the bots moving, the engine refused a trace whose
pass entity was -1. That is not a fault in the module: retail `jk2mp.exe`
compares the pass entity only against 1023, so a -1 walks into its entity array
at index -1 and reads whatever lies in front of it for an owner number. The
only defined reading of -1 is that there is no pass entity, which is what the
garbage amounts to in practice, so this engine says that deliberately instead
of reproducing it by reading out of bounds. The trace is served on its own for
that reason rather than handed to the shared dispatcher.

## What this does not say

Nothing here is a gameplay, rendering or wire claim. It is the shape of two
records, the offset of one field, and a count of which imports exist. No packet
is encoded, no entity is converted and no level spawns for this title yet.
