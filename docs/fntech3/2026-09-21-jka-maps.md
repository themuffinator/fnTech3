# Jedi Academy maps: RBSP v1 collision and its retail pak names

## Scope

This slice follows the [profile foundation](2026-09-21-jka-contracts.md) with
the two filesystem and asset facts a Jedi Academy profile needs before any
module or renderer work: the maps it reads, and the paks it must never offer
for download. Every map in a legitimate retail installation now reads through
the translator below, which is collision evidence: no map has been drawn, and
no runtime or rendering claim follows.

## RBSP version 1

Jedi Academy's maps are Raven's own format, not Quake III's: the identifier is
`RBSP` and the version is 1 (`codemp/qcommon/qfiles.h:307`). A profile now
accepts only its own maps -- `Com_GameManagerBspFormat` answers `COM_GAME_BSP_JKA`
for version 1 under a Jedi Academy profile and refuses every other version,
while no other profile accepts version 1 at all.

The directory carries eighteen lumps: Quake III's seventeen in the same order,
plus a light array at index 17 (`:356`-`:373`). Four of the records differ,
each because Raven carries four lightmap sets and their styles
(`MAXLIGHTMAPS` 4, `:441`):

| Record | Quake III (IBSP 46) | Jedi Academy (RBSP 1) |
| --- | --- | --- |
| Brush side | plane, shader (8 bytes) | plane, shader, draw surface (12 bytes) |
| Draw vertex | one lightmap coordinate and colour (44 bytes) | four of each (80 bytes) |
| Surface | one lightmap number, x and y (104 bytes) | four of each, plus lightmap and vertex styles (148 bytes) |
| Light-grid point | ambient, direct, direction (8 bytes) | four ambient and direct sets, four styles, direction (30 bytes) |

Entities, shaders, planes, nodes, leafs, leaf surfaces, leaf brushes, models,
brushes, draw indexes, fogs, lightmaps and visibility are byte-for-byte the
records Quake III already reads.

## Translation, and what it deliberately loses

`code/qcommon/bsp_rbsp.h` presents an RBSP map to the existing collision loader
as the IBSP 46 layout, the same approach the IHV profile's maps take. The
shared records are copied without interpretation, so a translated map keeps its
stored little-endian values on any host; the four differing records are
rewritten, keeping the first lightmap set. The map's own checksum, which peers
advertise, is taken from the installed file before translation and is unchanged
by it.

The translation is collision evidence only. It drops:

- the second, third and fourth lightmap sets and their styles, which is how
  Jedi Academy animates and blends lighting;
- the light array, which maps grid points to light-grid entries;
- the draw-surface reference on every brush side.

A renderer for these maps therefore cannot be built on this translation; it
needs a reader that keeps the styles and the light array. That gate stays open.

Bounds come before content: the header must be a full eighteen-lump directory,
every lump must lie inside the file without covering the directory, and each
fixed-size lump's length must be a whole number of its records. A lump length
that is not a whole number of records is a malformed file rather than an
unusual map, because a record size from the wrong format lands exactly there.
Indices inside records are left to the collision loader, which validates them
itself.

## Retail pak names

Raven numbered Jedi Academy's retail paks `assets0`-`assets8` rather than
`pak0`-`pak8`, and its own rule refuses that same set under a `missionpack`
directory, which it inherited from Quake (`codemp/qcommon/files.cpp:3166`,
`:3241`). The installation ships four of them -- `assets0.pk3` and
`assets1.pk3` with the content, `assets2.pk3` with the configurations and the
multiplayer modules, and `assets3.pk3`, the 1.01 patch. The engine's
official-pak rule is therefore profile-owned through a pak stem: a Jedi Academy
profile refuses `base/assets0`-`base/assets8` and
`missionpack/assets0`-`missionpack/assets8` and leaves Quake's numbered names
free, so a mod may still offer `base/pak0.pk3` while Raven's own content is
never downloaded from a server.

Multiplayer proves pure admission with the native `cgamex86.dll` and
`uix86.dll` pair, and its own rule marks a pak referenced for either of those
names as well as for Quake's `vm/cgame.qvm` and `vm/ui.qvm`
(`codemp/qcommon/files.cpp:1427`), so the engine's reference flag now marks
both for this title. That matters here more than for any other profile,
because Jedi Academy's multiplayer modules are themselves pak members: the
installation carries them in `assets2.pk3` and, patched, in `assets3.pk3`,
with no loose copy in `base/`.

## Evidence

| Check | Evidence |
| --- | --- |
| Retail maps | All 57 maps in a legitimate 1.01 installation carry `RBSP` version 1 and translate: 376,744 surfaces in all, 18,777 in the largest single map, with no map refused (`scripts/probe_jka_assets.py`) |
| Record sizes | Compile-time assertions on all four differing records and the eighteen-lump directory, against Raven's declared layout |
| Translation | A synthetic map with two surfaces, a patch, nine vertices, six brush sides, two light-grid points and four styles on everything translates with every shared lump byte-identical and every rewritten record carrying its first set |
| Malformed maps | Wrong identifier and version, six damaged lump directories, four record-size remainders, every truncated header length, a refused allocation and missing arguments are all refused without allocating or reading a record |
| Pak names | Both modes refuse all nine `assets` names in `base` and `missionpack`, accept Quake's numbered names, and refuse a server's `base/assets3.pk3` before a download plan is made |

Tests: `tests/jka_bsp_tests.cpp` (`meson test fntech3_jka_bsp`),
`tests/profile_pak_download_tests.py`, `tests/wolfet_download_tests.py`. The
installed sweep is `scripts/probe_jka_assets.py --installation <path>`, which
reads the installation, writes only below its `--output` directory and keeps no
retail payload.

No retail map, pak or asset is required, incorporated or shipped by any of it.
