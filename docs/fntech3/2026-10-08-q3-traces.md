# Quake III collision against the retail 1.32 server

The Quake III gate matrix's collision evidence was fnTech3's own: maps load,
damaged maps are refused, and earlier native probes traced a fixture box. This
record asks the retail `quake3.exe` 1.32 dedicated server and fnTech3's the
same questions through one synthetic native game module, on six stock maps:
75,240 traces, 8,640 of them around brush models linked as entities, plus
9,000 point contents, 96 entity links and 1,000 box queries. They agree
except for ten traces, at curves, tied brushes and very long traces, and
those come from the double-precision collision arithmetic fnTech3 carries from
Quake3e. No code changes here; the precision choice is left as a decision.
The [machine-readable record](2026-10-08-q3-traces.json) holds identities,
bounds, seeds, every tally and each of the ten traces.

## Method

The module (C, MSVC x86, kept in `.tmp` and not committed) exports
`dllEntry` and `vmMain` and calls Quake III's own syscall numbers. Its game
entity record is 1.32's 516-byte `sharedEntity_t`, whose shared half starts
with an unused 208-byte `entityState_t`. At `GAME_INIT` it binds its entities
and asks, through `G_TRACE`, `G_TRACECAPSULE`, `G_POINT_CONTENTS`,
`G_SET_BRUSH_MODEL`, `G_LINKENTITY` and `G_ENTITIES_IN_BOX`:

- **World:** four hulls -- a point, the player box, a random box up to 32
  units, and the player box traced as a capsule -- with three masks (solid,
  solid + player clip + body, and every bit), 300 each of a long trace between
  random points, a vertical drop through the world and a short trace of at
  most 48 units; then 1,500 point contents.
- **Brush models:** up to 32 of the map's brush models set on entities, moved
  and every second one turned, then linked; their link flags and bounds; 90
  traces around each; 200 box queries around them.
- **A box entity:** a player-sized entity with contents body, traced 300 times
  with box and capsule hulls.

Inputs come from a seeded generator and the module's own arithmetic. The
module prints every answer as raw float bits, then asks the server to quit.

The retail server runs `quake3.exe` 1.32 ("Q3 1.32 win-x86 Oct 7 2002") from
the Steam installation, read only, with `fs_homepath` in a scratch folder.
Its `Sys_LoadDll` (`0x447170`) looks for `qagamex86.dll` under `fs_basepath`
and then `fs_cdpath`, each with the game directory, so the module sits in a
scratch `fs_cdpath`'s `baseq3`. fnTech3's dedicated server loads it from its
home's `baseq3`. Both run `vm_game 0`, `sv_pure 0`, `bot_enable 0`, on
loopback on a private desktop. No installation file changed.

the same order, and 90 of the 96 links have bit-identical bounds; the other
six, turned models, are within 0.0005 units. The ten traces beyond:

- **q3dm1, player box, short trace:** retail stops at fraction 0.1964 on a
  plane facing (0.30, 0.66, -0.68), a curve facet's; fnTech3 stops at 0.2033
  on a 45-degree vertical plane, a bevel. The end positions are 0.32 units
  apart. Loading q3dm1, retail reports 9 invalid curve bevels and fnTech3 10.
- **q3dm1, player box, long trace starting in solid:** both stop at fraction
  0.0970. Retail stops on a curve facet, contents 1, at 0.096990; fnTech3 on a
  brush with contents `0x20000001` and surface flags 160, at 0.097008.
- **q3dm12, player box, every mask:** both stop at the same fraction and
  position on two brushes the trace enters at once; retail reports the player
  clip (contents `0x10000`, surface flags 17584), fnTech3 the solid brush.
- **Seven long traces** (q3dm1 four, q3ctf2 three), most starting in solid:
  the fraction differs by about 1e-5 over several thousand units, putting the
  end positions 0.01 to 0.07 units apart, with every flag equal.

Retail fact: a trace that touches an entity flagged `SVF_CAPSULE` drops the
retail level with "CM_ClipHandleToModel: bad handle 1 < 254 < 256": its
handle lookup knows no capsule handle. An earlier run of the module flagged
its box entity so and stopped retail there. No stock game flags an entity
that way. fnTech3 traces such an entity as a capsule, as the inherited
ioquake3 and Quake3e code does, and is not changed to drop.

## Where the differences come from

Observed in the Quake III 1.32 GPL source and fnTech3's: retail's
`CM_AddFacetBevels` builds each curve's edge bevels in float
(`VectorSubtract`, `CrossProduct`, `DotProduct`); fnTech3's, from Quake3e
through FnQuake3, builds them in double (`VectorSubtractDP`,
`CrossProductDP`, `DotProductDPf`). fnTech3's brush sweep uses double dot
products as well.

Inferences: double precision decides some curve bevels the other way -- the
extra invalid bevel on q3dm1 -- and so the plane a trace meets beside a curve,
and it breaks ties between brushes a trace enters at the same fraction
differently. The long traces' differences are the same arithmetic over a long
distance. Matching retail exactly would mean float bevels and float dot
products in the collision code every profile shares. That would undo a
deliberate upstream precision change, so it is left as a decision rather than
made here. The differences are rare: ten traces in 75,240.

## Limits

- No zero-length trace (position test), client entity or pass entity is
  compared.
- Six of the stock maps; Team Arena and third-party maps are not traced.
- Quake Live's engine is not compared; its game module ABI differs.
