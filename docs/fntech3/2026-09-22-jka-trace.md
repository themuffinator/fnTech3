# Jedi Academy's trace record, and what its module actually asks for

*2026-09-22. Measured from a legitimate retail Jedi Academy 1.01 installation.
The installation was read, never written. Nothing here is taken from any other
engine's source: every number below was read out of the retail module's own
code, and the method for reading it is given so it can be checked.*

## The finding that matters

**Jedi Academy's `trace_t` is 48 bytes and is not Quake III's.**

Raven packed the two solid flags and the entity number into the first four
bytes. Everything from the fraction onwards therefore sits *four bytes earlier*
than Quake III puts it.

| offset | Jedi Academy | Quake III at the same offset |
|--:|---|---|
| 0 | `byte allsolid` | `int allsolid` |
| 1 | `byte startsolid` | — |
| 2 | `short entityNum` | — |
| 4 | `float fraction` | `int startsolid` |
| 8 | `vec3 endpos` | `float fraction` |
| 20 | `cplane_t plane` | `vec3 endpos` (12), `cplane_t plane` (24) |
| 40 | `int surfaceFlags` | `cplane_t` tail |
| 44 | `int contents` | `int surfaceFlags` |
| 48 | *(end)* | `int contents` (48), `int entityNum` (52) |

An engine that handed this game a Quake III trace would put the fraction where
the game reads two flags and an entity number, and the endpoint where it reads
the fraction. Every trace in the game would be wrong, and nothing would say so.

The plane inside it *is* Quake III's, unchanged: `vec3 normal` at 20, `float
dist` at 32, `byte type` at 36, `byte signbits` at 37, two bytes of padding.

## How it was measured

The module reaches the engine through one function pointer. Every import is a
small wrapper that pushes the import's number and calls it, so the wrappers can
be found by looking for that call and reading the push in front of it.

`trap_Trace` is the wrapper at RVA `0xa6180`. It is called from **233** places
in the module. For each of those call sites the results pointer is produced by
a `lea` immediately before the last `push` — so the address of the caller's own
trace record is known, relative to its stack pointer. Tracking the stack
pointer forward from the call then says, for every later access, which byte of
the record it lands on and how wide it is.

**203 of the 233 call sites** could be followed far enough to be counted. The
accesses fall out like this:

| offset | accesses | widths seen |
|--:|--:|---|
| 0 | 97 | 58 as one byte (the rest take the record's address) |
| 1 | 61 | 61 as one byte, never wider |
| 2 | 54 | 54 as a sixteen-bit word, never wider |
| 4 | 96 | 96 as a four-byte float, never otherwise |
| 8, 12, 16 | 43, 46, 60 | four bytes |
| 20, 24, 28 | 9, 20, 17 | four bytes |
| 32 | 3 | four bytes |
| 36, 37 | 6, 2 | one byte |
| 40 | 12 | four bytes |
| 44 | 2 | four bytes |
| 48 and up | few, scattered | *(the caller's next local, not this record)* |

Offsets 0 and 1 are only ever read a byte at a time. Offset 2 is only ever read
as a word. Offset 4 is only ever read as a float. Offsets 36 and 37 are only
ever read as bytes, which is what a plane's type and signbits are. That is the
packed head, the fraction where Quake III has a flag, and the plane four bytes
early -- read off the module's own instructions, at ninety-six independent
sites for the fraction alone.

The script is kept with the session's working files; re-running it against the
same module reproduces the table above.

## What the trap passes

Academy's `trap_Trace` takes Quake III's seven arguments and passes **nine**:

    syscall( G_TRACE, results, start, mins, maxs, end, passEntityNum,
             contentmask, 0, 10 )

The trailing `0` and `10` are constants the wrapper supplies; they steer Ghoul2
collision, which the world trace has none of. fnTech3 records them and does not
act on them. `G_G2TRACE`, import 28, passes all nine from its caller and is
where they would mean something.

Import 49, `G_TRACECAPSULE`, has **no wrapper at all** in the retail module:
this game never asks for a capsule trace.

## The import inventory: 150 of 329

The same wrapper scan gives something more useful than one record. The module
carries a call thunk for exactly **150** of the game import numbers, and it can
never call any other. That is the whole of what this title asks the engine for:

    0 1 5-30 32 34-38 40-44 48 52-55 59 61-78
    202-206 209-214 217 220 221 223 225 227 229 232 233 235 236 241
    250 251 260 261
    400 401 406-409 411 414-419 421 422 424 425
    525 526 546 547 548 551 555 556 561 562 563
    582 585 587 589 590 591 593-598 600 601 603-607 609 612 615
    622 623 625 627-634

Three things follow, and none of them is a guess:

1. **Academy's bots do not use area awareness.** Not one number in the AAS
   block at 300-318 has a thunk. The installation confirms it from the other
   side: it ships no `.aas` file for any map.
2. **Academy's bots do not use Quake III's configured AI either.** They never
   load a character (500-506), never allocate a chat state (507-524), and the
   installation ships none of `items.c`, `weapons.c`, `syn.c`, `rnd.c` or
   `match.c` -- only Raven's own `botfiles/*.jkb` and `bots.txt`. What they do
   ask for is the state machinery (546, 547, 548, 551, 555, 556, 561, 562, 563
   and the two resets at 525 and 526) driven through the elementary-action
   block at 400-425. fnTech3's profile for this title now says exactly that.
3. **Navigation is Raven's own**, at 202-241, and the module never calls
   `G_NAV_INIT` or `G_NAV_FREE`: it expects the engine to hold a graph that
   either came from a `.nav` file or was built by the module itself through
   `G_NAV_ADDRAWPOINT`, `G_NAV_HARDCONNECT` and `G_NAV_CALCULATEPATHS`.

## Trajectories, while the same method was to hand

`BG_EvaluateTrajectory` begins at RVA `0x4ac70`, bounds its switch with
`cmp eax, 6` and dispatches through the table at `0x4ae9c`, so the type has
exactly seven values. Each case was read for the arithmetic it does:

| value | what its body computes | meaning |
|--:|---|---|
| 0, 1 | the same body: copy `trBase` | stationary, interpolated |
| 2 | `base + delta * t`, `t` in seconds | linear |
| 3 | the same, after clamping `t` to `trDuration` and to zero | linear stop |
| 4 | `t` scaled to ninety degrees through `pi/180`, passed to sine | **Raven's own** |
| 5 | a phase built from two pi, passed to sine | sine |
| 6 | `base + delta * t`, then `result[2] -= 400 * t * t` | gravity |

Raven inserted its own type at 4. **Academy's sine and gravity are 5 and 6, not
Quake III's 4 and 5.** A record converted on the assumption that the first six
coincide would make every falling object oscillate. The table is frozen in
`code/compat/jka_trajectory_types.def` and the two renumbered values are held
by a `static_assert` in the adapter.

## The engine's own table, and a cross-check that came out exactly

Retail `jamp.exe` dispatches the game's imports from one function. It bounds
the number with `cmp eax, 0x27a` -- **634** -- and jumps straight through a
635-entry table at `0x45d34c`, with no byte-index level: Academy's game import
space is 0 to 634, and the 796 figure quoted elsewhere is the whole of its
module tables together, game, cgame and user interface, imports and exports.

Counting the slots that do not land on `Bad game system trap` gives **329**
handled numbers. fnTech3's frozen table for this title names **329**. They are
not merely the same count: the two sets are *identical* -- every number the
retail engine handles is named here, and every number named here is handled
there, with no extras on either side. The table was built by another means
entirely, so this is an independent confirmation of all 329 rows at once.

### What the animation handler takes

The same table names what the frontier needs. Import 596, the call that stops
a bot from spawning, is handled at `0x45cc63`. It reads ten arguments and
converts exactly one of them -- `args[3]` -- from a module address:

    G_G2_PLAYANIM( ghoul2, modelIndex, boneName, startFrame, endFrame,
                   flags, animSpeed, currentTime, setFrame, blendTime )

Ten arguments is what the module's own wrapper passes, and one pointer is what
the handler converts, so the only pointer in that list is the bone's name. Its
neighbours read the same way: 593 takes three with the name as its one pointer,
595 takes eleven with three, 597 takes ten and converts seven -- an out-parameter
call -- and 615 takes three, copying a fourteen-word record out of `args[3]`
before passing it on. None of those is served; they are recorded so that when
they are, the shape comes from the engine rather than from a guess.

## What this does not say

Nothing here is a gameplay, rendering or wire claim. It is the shape of two
records and a count of which imports exist. Whether fnTech3 answers any of
those imports correctly is a separate question, answered by
`docs/fntech3/COMPATIBILITY.md` and by the tests each answer carries.
