# Key names

## Scope

This record covers the names this engine writes and reads for key numbers: the
table that `Key_StringToKeynum` and `Key_KeynumToString` search in
[`code/qcommon/keys.c`](../../code/qcommon/keys.c), which the console, the
config each profile writes, `bindlist`, and every profile's key-name imports all
pass through. It corrects the five rows where that table disagreed with both
retail tables, and removes the second copy of Enemy Territory's key numbers.

Key numbers themselves are unchanged; the
[key-number record](2026-09-19-q3-key-numbers.md) covers those, and this record
closes the naming differences it left open.

Not covered: runtime input. No game was given keyboard input for this record.

## Observed

### The two retail tables

Both retail engines search one `{name, keynum}` table.
`scripts/probe_q3_key_numbers.py` walked each of them for the
[key-number record](2026-09-19-q3-key-numbers.md): quake3.exe 1.32's holds 107
rows at `0x4bf950`, quakelive_steam.exe's 111 at `0x565b88`, and the only names
in Quake Live's table absent from Quake III's are `MOUSE6`-`MOUSE9`. Quake
Live's table is therefore Quake III's plus those four rows, so the two agree on
every name below the mouse buttons. That last step is an inference from the
recorded row sets, not a separately observed fact.

The five rows where this engine's table disagreed with both of them:

| Key | quake3.exe | quakelive_steam.exe | fnTech3 before | fnTech3 now |
| --- | --- | --- | --- | --- |
| 130 `K_POWER` | `0x82` | `0x82` | `POWER` | `0x82` |
| 157 `K_F13` | `0x9d` | `0x9d` | `F13` | `0x9d` |
| 158 `K_F14` | `0x9e` | `0x9e` | `F14` | `0x9e` |
| 159 `K_F15` | `0x9f` | `0x9f` | `F15` | `0x9f` |
| 176 `K_KP_STAR` | `KP_STAR` | `KP_STAR` | `0xb0` | `KP_STAR` |

`K_KP_STAR`'s row had been commented out since the initial commit, inherited
from this engine's FnQuake3 and Quake3e lineage. The other four are names that
lineage added.

### What each difference cost

- A retail config line `bind KP_STAR ...` did not load. `Key_StringToKeynum`
  returned -1, `Key_Bind_f` printed `"KP_STAR" isn't a valid key`, and the next
  `writeconfig` wrote the config back without the line, so the binding was lost
  rather than kept unread.
- `bind POWER ...` and `bind F13 ...`-`bind F15 ...`, which this engine wrote
  into its own config, are names neither retail engine knows. Retail dropped
  those lines the same way, so a config written here did not survive a return
  to either retail engine.

### Enemy Territory's key numbers

`code/compat/wolfet_keycodes.def` repeated all 110 rows of
[`rtcw_keycodes.def`](../../code/compat/rtcw_keycodes.def), number for number.
ET's numbers are Quake III's, which RTCW kept as well, so the two files were the
same table written twice and could drift apart unobserved.

## Correction

- `keynames` holds `KP_STAR` for 176 again, and no longer holds `POWER`, `F13`,
  `F14` or `F15`. `Key_KeynumToString` writes those four as `0x82` and
  `0x9d`-`0x9f`, as both retail engines write them, so a config written in any
  profile now loads in both of them.
- A second table, `keyaliases`, holds those four names, and
  `Key_StringToKeynum` scans it after `keynames`. A config an earlier build of
  this engine wrote still loads, and so does one from its FnQuake3 or Quake3e
  lineage. Nothing writes those names back: `Key_KeynumToString` does not read
  that table, and `Key_KeynameCompletion` still offers only `keynames`, the
  names this engine writes.
- [`wolfet_keycodes.def`](../../code/compat/wolfet_keycodes.def) names RTCW's
  table through ET's own macro instead of repeating its rows. ET's provenance,
  and its note that ET's `K_LAST_KEY` terminator is a count rather than a key,
  stay in the file.

The key numbers, the per-profile adapters, the module key imports and the input
producers are untouched.

## Results

### Tests

- [`tests/key_name_source_tests.py`](../../tests/key_name_source_tests.py) pins
  the corrected table: `KP_STAR` named, the four names present only in
  `keyaliases`, `Key_KeynumToString` reading only `keynames` and
  `Key_StringToKeynum` reading both, in that order. Its probe compiles both
  tables and both functions and checks that 176 is named `KP_STAR` and parses
  back in either case, that 130 and 157-159 are written as retail's hex and
  parse back from it, that their names still load, that no key in `MAX_KEYS` is
  ever written as one of them, and that every name in either table reaches its
  own key. Commenting `KP_STAR` out again fails it.
- The key, RTCW key-name, WebUI and input source suites pass unchanged: 151
  tests over `key_name_source`, `q3_key_numbers`, `rtcw_key_names`,
  `webui_wiring` and `input_system_source`, with Clang 20.1.7 compiling the
  probes.
- A disposable probe compiled `wolfet_key_adapter.h`, `rtcw_key_adapter.h` and
  `q3_key_adapter.h` in one translation unit and checked all 110 ET rows
  against RTCW's constants and through all three adapters, from the repository
  root and from `tests/`, so both include forms in the tree resolve.

## Differences

- The console and the config keep this engine's key vocabulary for both
  spellings of a key: `bind MOUSE6` and `bind 0xb7` are the same key here, and
  `bind 0xe9` binds `AUX13`, which quake3.exe has no key for. Neither retail
  table leaves a key above 175 unnamed, so neither retail engine writes a
  hexadecimal name above `0x9f` and no config either of them writes can carry
  one. A name is the portable spelling in both directions.
- A `KP_STAR` line now loads, survives a rewrite and shows in `bindlist`, but
  the key does not fire. All three producers report the keypad's `*` as `'*'`,
  and so does retail: quake3.exe's Win32 and X11 producers both leave it a
  character, as RTCW SP, RTCW MP and ET do, and only the Mac clients report
  `K_KP_STAR`. A named key that no producer reports is retail's own
  arrangement on Windows. The [keypad star record](2026-09-20-keypad-star.md)
  records that reading, the maintainer's decision to keep the character, and
  the pins that hold it; the name and the key are separate questions.
